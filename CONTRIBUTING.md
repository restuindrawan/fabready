# Contributing to fabready

Thanks for helping. fabready is small and opinionated: it checks KiCad boards before they're ordered, it never
sends your design anywhere, and it only changes your files when you ask it to. Contributions that keep it that
way are very welcome.

## Ways to help

- **Report a false alarm or a missed problem.** Say what fabready reported (or didn't), what was actually wrong
  or right, and attach the `.kicad_pcb` if you can share it. A cut-down board that still shows the problem is
  even better.
- **Add a part** to the component library (see [Parts](#adding-a-part)). Typical datasheet values for common
  regulators, LEDs, MOSFETs and so on make the parts review useful for more boards.
- **Add a check or an automatic fix** (see below).
- **Improve the docs.** If something in `docs/` confused you, it'll confuse the next person too.

For anything bigger than a small fix, open an issue first so we can agree on the approach before you spend
time on it.

## Setup

You need:

- **Rust** (stable) for everything.
- **Python 3** to regenerate the sample boards.
- **Node.js** for the desktop app (Tauri's CLI), and to try Claude Code or Codex in the app's Agent tab.
- **KiCad** (optional). When `kicad-cli` is installed, its DRC and ERC are merged into the report.
- **OpenCode** (optional). With it installed, a test talks to a real agent over ACP.

```bash
cargo test --workspace                     # unit, sample-board and MCP end-to-end tests
cargo clippy --workspace --all-targets     # must stay warning-free
cargo run -p fabready-cli -- check samples/macropad-buggy

cd app && npm install && npx tauri dev     # run the desktop app
```

The app's frontend (`app/ui/`) is plain HTML, CSS and JavaScript with no build step. While `tauri dev` is
running, reload the window from the web inspector (right-click → Inspect) to pick up changes. Other debug
builds embed `app/ui`, so rebuild them after editing it.

## How the code fits together

| Path | What |
|---|---|
| `crates/fabready-core` | The engine: KiCad parser, checks, fixes and edits, parts review, SVG/PNG renderer, report, MCP server, and the board viewer shared with the app (`assets/`) |
| `crates/fabready-cli` | The `fabready` command |
| `app/` | The Tauri desktop app: Rust commands and the agent client in `src-tauri/`, the UI in `ui/` |
| `samples/` | Boards generated by `samples/generate.py`: clean and buggy keyboard macropads, and a sensor board with component problems |
| `docs/` | User documentation |

[AGENTS.md](AGENTS.md) has the detailed map: where each kind of change goes and the conventions each part
relies on. It's written for AI coding agents, but it's the most complete description of the codebase, so read
it before a larger change.

## Common changes

### Adding a check

1. Write it in `crates/fabready-core/src/` next to similar checks (`fab.rs` for manufacturing limits,
   `connectivity.rs` for wiring, `keyboard.rs` for keyboard boards, `parts.rs` for components).
2. Register its id, title, why it matters and how to fix it in `findings::CATALOG`. `fabready explain <id>`
   and the agents' `explain_check` read it from there.
3. Plant the mistake in the buggy sample: edit `samples/generate.py`, run `python3 samples/generate.py`, and
   commit the regenerated boards.
4. Assert that the check catches it in `crates/fabready-core/tests/samples.rs`, and that the clean sample
   still passes.
5. Describe it in the matching page in `docs/`.

Aim for checks that are right on real boards. A noisy check teaches people to ignore fabready. When the
geometry is ambiguous, prefer a warning, and say in the message what to look at.

### Adding an automatic fix

Automatic fixes live in `crates/fabready-core/src/fixes.rs`. A check attaches `.fixable("<kind>:...")` to its
finding, and `fixes::plan` turns that id into byte-range edits of the `.kicad_pcb`. Only add fixes that need
no design judgement: widening a track to the fab's minimum is fine, while re-routing is not. Keep edits
surgical, so the rest of the file stays byte-for-byte the same, and test preview, apply and undo the way
`fixes_preview_apply_and_undo` does.

### Adding a part

Common parts go in `LIBRARY` in `crates/fabready-core/src/parts.rs`, with typical values from the
manufacturer's datasheet. Use the manufacturer's own datasheet, not a distributor scrape, and note anything
unusual in a comment. See [docs/parts.md](docs/parts.md) for how ratings are matched and used.

### Changing the board viewer or the app

- The viewer (`crates/fabready-core/assets/viewer.{js,css}`) is shared: it's embedded in the exported
  `viewer.html` and served to the app. Change it in one place, and check both. Run
  `fabready check samples/macropad-buggy` and open `samples/macropad-buggy/fabready-out/viewer.html`.
- The renderer and the viewer meet at the SVG's attributes (`data-layer`, `data-item`, `data-net`). Keep
  those when changing `render.rs`.
- Check the app in both light and dark mode, and with a narrow window.
- If you add a setting, add it to `config::Config`, the Settings tab and
  [docs/configuration.md](docs/configuration.md).

### The MCP server and the agent chat

The MCP tools are in `crates/fabready-core/src/mcp.rs`, with an end-to-end test in
`crates/fabready-cli/tests/mcp.rs`. The app's agent chat is an ACP client in `app/src-tauri/src/agent.rs`.
`FABREADY_TEST_PROMPT=1 cargo test -p fabready-app` sends a real prompt through OpenCode when it's installed.
That uses your own OpenCode providers, so it's off by default.

## Ground rules

- **No network requests from fabready.** The parts review works from the board and a built-in library. Don't
  add calls to online services, and never to unofficial or scraped endpoints. The agent chat is the one place
  that talks to the outside world, through the agent the user picked.
- **Don't change the user's files unless they asked.** Writes go through the fix and edit machinery, with a
  backup and undo.
- **Dependencies must be under a license listed in `about.toml`.** `cargo about generate about.hbs -o
  THIRD_PARTY_LICENSES.html` fails otherwise. See [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md). Prefer the
  standard library when a dependency would only save a few lines.
- **Match the surrounding code.** Its lines are longer than rustfmt's default, so don't run `cargo fmt` over
  whole files; it would bury your change in reformatting. Comment the why, not the what.
- **Update the docs with the change.** User-facing behaviour goes in `docs/`. Keep `README.md` to the
  overview, quick start, privacy, disclaimer and license.

## Pull requests

- One topic per pull request. Describe what changed and why, and how you tested it. Include a screenshot for
  UI changes.
- `cargo test --workspace` and `cargo clippy --workspace --all-targets` must pass with no warnings.
- If you changed the sample boards, commit what `samples/generate.py` produces rather than hand edits. It's
  deterministic, so re-running it shouldn't change anything else.
- Don't commit `fabready-out/`, `target/` or `THIRD_PARTY_LICENSES.html`.
